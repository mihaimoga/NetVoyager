NetVoyager

Introduction

NetVoyager is a lightweight network diagnostics app that lets users quickly assess connectivity and trace routes. With built-in ping and traceroute tools, it helps identify latency issues, unreachable hosts, and visualize packet paths. Ideal for IT pros, engineers, and curious users, with a clean UI and real-time results. NetVoyager is written in C++ and uses pure Win32 API and STL which ensures a higher execution speed and smaller program size. By optimizing as many routines as possible without losing user friendliness, NetVoyager is trying to reduce the world carbon dioxide emissions. When using less CPU power, the PC can throttle down and reduce power consumption, resulting in a greener environment. I hope you enjoy NetVoyager as much as I enjoy coding it!

Getting started

Install NetVoyager using the installer

  • Download the installer
  • Run the executable binary and follow the installation flow

The installer will likely require Administrative privileges in order to install NetVoyager (and later, to update NetVoyager or install or update plugins, or anything else that requires writing to the installation directory). If you do not have Administrative privileges, you either need to tell the installer to use a location where you do have write permission (though that may still ask for Administrator privileges), or you may choose not use the installer and instead run a portable edition from a directory where you have write permission.

Install NetVoyager from zip

These instructions will allow you to run a portable or mini-portable (also called “minimalist”), without requiring administrative privileges.

  • Create a new folder somewhere that you have write-permission
  • Unzip the content into the new folder
  • Run NetVoyager from the new folder

The portable zip edition of NetVoyager can be removed by deleting the directory they came in. If you manually set up file associations or context-menu entries in the OS, it is your responsibility to remove them yourself.

Application's menu

The NetVoyager menu features the application's most important functions:

  • Ping with live latency, packet loss, and summary stats.
  • Traceroute to visualize the path to any host and identify slow or unreachable hops.

Roadmap

These are ideas for future versions of NetVoyager, not commitments, and none of them has a release date. If you would like to work on one of them, please see the next section and open or comment on an issue first.

Export results to JSON or CSV

Today a run exists only as formatted text in the results page. Exporting will let you save it, compare it over time, attach it to a ticket or open it in a spreadsheet.

  • Ping: one record per echo request with the sequence number, UTC timestamp, target, replying address, host name (when reverse DNS is enabled), packet size, round-trip time and status.
  • Traceroute: one record per hop with the hop number, address, host name, minimum, average and maximum round-trip time, and a status (reply, timed out or error).
  • Run details and summary: the NetVoyager version, start and end time, probe type, target, IP version and the settings in use, plus the number of requests sent, received and lost, the loss percentage and the minimum, average and maximum round-trip time.
  • Formats: JSON (UTF-8, with a schema version and null for missing values) and CSV (RFC 4180, UTF-8 with a byte order mark so that Excel opens it correctly, and . as the decimal separator whatever your regional settings are).
  • Timeouts are never exported as 0: a request that timed out has an empty (CSV) or null (JSON) round-trip time, while a reply shown as <1ms is exported as 0.
  • Commands: Export CSV… and Export JSON… on the Home tab, available when a run has finished and no ping or traceroute is running.

Text that comes from the network or from the system, such as host names and error messages, is escaped for each format, and CSV text cells that a spreadsheet could interpret as a formula are neutralized. Command-line or scheduled export, XLSX/XML and exporting while a run is still in progress are out of scope for a first version.

Done when: the files open cleanly in a spreadsheet and in a JSON parser, the values match the screen for IPv4 and IPv6 runs of both probes, and timeouts are never shown as 0.

Dark theme and accessibility improvements

The window and the results page stay light whatever the Windows app mode is, and some parts of the interface, such as the links in the About dialog, cannot be reached from the keyboard.

Dark theme

  • A System (default), Light or Dark setting, remembered between sessions and applied without restarting.
  • With System, NetVoyager follows the Windows app mode at startup and when it changes while the application is running.
  • The results page follows the chosen theme, without a white flash while a page loads.
  • The ribbon, status bar and window frame (including a dark title bar) follow the theme and step aside when a Windows high-contrast theme is active. Standard dialogs may stay light in a first version.
  • Open questions: the start page is a remote page that the application cannot theme, so it may be replaced by a local themed page, and the results page loads Bootstrap from a CDN and is unstyled when you are offline, so a small bundled stylesheet may be added.

Accessibility

  • Keyboard: shortcut keys and ribbon KeyTips for Ping and Traceroute, About dialog links that can be reached with Tab and activated with Enter or Space, and access keys in the hostname prompt.
  • Results as a table: ping samples and traceroute hops written as a real HTML table with a caption and header cells, so that columns line up and screen readers can announce the row and column of each value.
  • Announcements: the start, completion and failure of a run are available to screen readers, and the Please wait dialog gets a text label.
  • Contrast and scaling: at least 4.5:1 text contrast in both themes, support for Windows high-contrast themes and forced colors, an evaluation of per-monitor DPI awareness, and a check of the results page at 200 % zoom.
  • Testing with Narrator, NVDA and Accessibility Insights for Windows.

Done when: every command is reachable from the keyboard, results are exposed as a table, automated accessibility checks report no failures, the application is readable in both themes and under a high-contrast theme, and the theme follows Windows at startup and when it changes.

Continuous Integration (GitHub Actions)

The repository has no automated build yet. NetVoyager has four build configurations (Debug and Release for x64 and Win32) and needs a specific toolchain (Visual Studio 2026, MSVC v145 and statically linked MFC), so a change that breaks one configuration is easy to miss.

  • A GitHub Actions workflow runs on pushes, pull requests and on demand, on a hosted Windows runner image that includes Visual Studio 2026 and is named explicitly so that the toolchain does not change silently.
  • It restores the NuGet packages (WebView2 and the Windows Implementation Library), then builds NetVoyager.vcxproj for Debug|x64, Release|x64, Debug|Win32 and Release|Win32. MSBuild cannot build the installer project, so the MSI stays a manual step until the installer moves to something MSBuild can build.
  • The Release NetVoyager.exe and WebView2Loader.dll are uploaded as workflow artifacts.
  • The workflow uses read-only repository permissions and pinned actions, which Dependabot keeps up to date. New WebView2 versions, a recurring item in the release notes, are reported by Dependabot if it supports this native project, or by a scheduled job.
  • It begins by failing only on build errors and then tightens for new code-analysis warnings; once stable, the check is required before a pull request can be merged.
  • Later: CodeQL for C++, a tag-triggered release workflow that also produces the portable zip, and a build status badge.

Done when: a pull request that breaks any of the four configurations shows a failing check, and a successful run on the default branch produces downloadable Release artifacts.

How the ideas fit together

  • Continuous Integration is independent of the others and guards every change that follows, so it is a good first step.
  • Export introduces a structured copy of each run's results, which the accessible results table can reuse.
  • Dark theme is independent of both and can proceed in parallel.

Create and Submit your Pull Request

As noted in the Contributing Rules for NetVoyager, all Pull Requests need to be attached to a issue on GitHub. So the first step is to create an issue which requests that the functionality be improved (if it was already there) or added (if it was not yet there); in your issue, be sure to explain that you have the functionality definition ready, and will be submitting a Pull Request. The second step is to use the GitHub interface to create the Pull Request from your fork into the main repository. The final step is to wait for and respond to feedback from the developers as needed, until such time as your PR is accepted or rejected.
